## Answers in short

- **The other services.** Each keeps running alone, unchanged for a person on one computer (Zen 10). Behind Latarnik a tool's server listens on 127.0.0.1, takes the client's address only from Latarnik's forwarded headers, writes relative links and answers `nogat-server/1`; Latarnik adds the public duties once for all (limits, caching, CORS, logs) and never serves more than a tool does (S7, the table per tool).
- **Talking through the API.** One address: `GET /api/v1/server` lists the services and the base of each one's API; a command is called at `/<tool>/v1/<group>/<verb>` under the name its tool's catalog gives it, the tool's envelopes and errors passed through unchanged; long work is a job, `nogat-job/1`; a chain of several tools is one call, `POST /api/v1/flows/<name>` (level 2).
- **Computation apart from the GUIs.** Yes. Every GUI becomes files that call their tool's `/api/v1`, and every number comes from a tool's server: Hydrolog's for hydrology, Obserwator's for station data, Hydrograf's for terrain, Kartograf's for download plans. Today two GUIs compute inside their own GUI server behind a private API (Obserwator, Hydrolog), while Hydrograf's and Archiwista's are already files over their APIs (Facts).

## Design [proposed]

### L0. Optional, and every tool alone

Latarnik is a new project (`https://github.com/Daldek/Latarnik`, created by the author; profile `app`), optional in every deployment. Every tool keeps its CLI, MCP, library, server and GUI, `<tool> gui serve` one command on 127.0.0.1, and depends on nothing of Latarnik; Latarnik imports no tool and reaches each over HTTP only. Latarnik computes nothing: it routes, checks, limits, caches, logs and chains calls; a step that needs logic (a condition, arithmetic, geometry) is a tool's command.

### S. What a tool's server provides

S1. **Versioned REST from the catalog.** Every command with a route at `/api/v1/<group>/<verb>` (AGI-6.1); `server` and `jobs` are reserved and never a catalog group. The route is the catalog's: commands-1 and command-list-1 gain an optional `rest` (`{method, path}` or `null`), and command-list-1 entries `effects` and `check` (additive, AGI-4.1; Obserwator's list carries them flat today). `rest.method` is `POST` for a read-only command whose inputs a URL cannot carry (an object such as a geometry or a network, a long array such as a series); such a route stays read-only and needs no key (an amendment of AGI-6.1). OpenAPI also at `/api/v1/openapi.json`, Archiwista's place, with a relative `servers` URL, so that it reads right through a prefix (an amendment of AGI-6.2). An option with `path_role` is local: a server refuses it, as Obserwator's refuses server and local options (`api/routes/commands.py:29`), and takes its inline form.

S2. **The catalog decides access and caching**, in the tool's server and again in Latarnik:

| Command (catalog `effects`, `check`) | Access | Latarnik caches |
|---|---|---|
| `read_only`, no `network` | public | by the tool's `Cache-Control`, `ETag` and `Vary`, `public` answers only |
| `read_only`, `network` | public only through the tool's own cache of the provider: a snapshot or a cache per key of bounded age, as Obserwator's GUI has (`gui/_live.py`); never one provider request per client request | at most for the cache's remaining life |
| a plan, `POST …?check=true` of a command that is its own `check` | public where the tool serves it: Kartograf's plans under its plan limits (its D5); Obserwator's public mode refuses them (Goniec S2) | no |
| not `read_only` | the tool's key, `X-API-Key` (AGI-6.5), required by Latarnik (`401 unauthorized`) and checked by the tool in constant time; Latarnik keeps no tool's key | no |
| `destructive` | the key and the command's own `force` | no |

S3. **Envelopes.** An answer is the tool's `<tool>-result/1` (AGI-4.2) or an attachment named as DEV-19.21 says; an error is `application/problem+json` with the fields of `<tool>-error/1` (AGI-6.3); texts follow `Accept-Language` (AGI-6.4); providers' lines as DEV §20. Latarnik passes bodies unchanged and answers its own errors in the same form: `rate_limited`, `source_unavailable` for a service that is down or past its time, `not_found`.

S4. **Discovery, `nogat-server/1`, at `GET /api/v1/server` on every server**, a tool's own and Latarnik alike, so that one request finds every service (agreed on 2026-11-24 with the review of the Goniec plan and with Kartograf's plan): `services`, one entry on a tool's own server and one per service behind Latarnik, each with `tool`, `version`, `api` (each major served and its base: `{"1": "/api/v1"}` alone, `{"1": "/obserwator/v1"}` behind Latarnik; a URL reference, absolute for a service on another host), `capabilities`, `ogcapi`, `instance`, `terms`, `attribution`, `terms_notice` (the Goniec plan's S4) and `gui`, the address of its GUI where it has one; on Latarnik also `release_set` and `flows`. The schema `schemas/exchange/server-1.schema.json`, additive within `/1` (AGI-4.1). A GUI finds its own API base as its tool's entry there, one request on either server (Kartograf's D7).

S5. **Behind Latarnik.** A server listens on 127.0.0.1 (Obserwator's REST default changes); it takes the client's address and scheme only from `X-Forwarded-For` and `X-Forwarded-Proto` sent by a trusted proxy, set by one setting, `127.0.0.1` by default (uvicorn's `FORWARDED_ALLOW_IPS` in Obserwator and Hydrolog, `trusted_proxies` in Archiwista; Hydrograf moves from `X-Real-IP` and `CF-Connecting-IP`), the install contract's rule 3; and it writes only relative links and `Location` headers (a job's `Location: jobs/<id>`, OGC `links`), so its documents read right behind any prefix and Latarnik rewrites no body. Its own limits (DEV-15.9) and logs (DEV §12) stay as the backstop.

S6. **Jobs, `nogat-job/1`**, a new contract on Archiwista's model:

- `POST /api/v1/jobs` with `{"command": "<group> <verb>", "options": {…}}`, access as S2 gives for that command, answers `202`, `Location: jobs/<id>` and the job's document;
- `GET /api/v1/jobs/<id>` answers `nogat-job/1`: `id`, `tool`, `command`, `state` (Archiwista's seven), `progress` (`done`, `total`, optional), `created_at`, `started_at`, `finished_at`;
- `GET /api/v1/jobs/<id>/result` answers, once the job has ended, what the command's synchronous route would (the envelope, an attachment or the error's problem document), and before that `409 conflict` with the reason `job_running`;
- `POST /api/v1/jobs/<id>/cancel` answers `202`; `GET /api/v1/jobs/<id>/events`, server-sent events resumed after `Last-Event-ID`, MAY be served.

The id is 128 random bits and the only way to a job (no list of other clients' jobs). An ended job stays at least an hour, then `404 not_found` with the reason `job_expired`; a result of a person's choices is held in memory only (ECO-059); a restart ends a running job `interrupted`. Each client has at most 2 active jobs. A command whose run can outlast a request carries `long: true` in its catalog (optional in commands-1) and is served only as a job: its synchronous route answers `409 conflict`, reason `run_as_job`. MCP keeps its progress notifications (AGI-5.11). First jobs: Obserwator's `store sync`, `series build`, `analyses build`, `pmaxtp sync`; Hydrolog's `commands batch` and a large `route network`; Hydrograf's hydrographs and networks of large catchments; later Hydraulik's model runs.

### L. Latarnik

L1. **Hosts and routes.** Latarnik listens on 127.0.0.1 behind the host's one edge, which keeps TLS (the install contract's rule 12; question 1). Each GUI keeps its own host, so its own origin: today's `obserwator-test`, `hydrolog-test`, `hydrograf-test` and `archiwista-test`, and Kartograf's. On a GUI's host Latarnik passes every request to the tool's server, serving from its cache what may be cached (L5), so a GUI, its admin paths and the edge's Access rules are the same alone and behind Latarnik. On one computer Latarnik gives each GUI a port of its own, stage 2's front ports. Latarnik's own host:

| Route | What |
|---|---|
| `/` | the hub: the deployment's GUIs, each with its mark and one line, opened in its own tab (DEV-15.4); a public GUI itself, with its regulamin and the rest of DEV-15.7 to DEV-15.13 |
| `GET /api/v1/server` | `nogat-server/1` of every service, built from each tool's own with `api` mapped to `/<tool>/v1`, refreshed at start and every minute |

L2. **At the door**, once for every service, what each public GUI does today on its own:

- limits per client address as DEV-15.9 (300 requests in 60 s by default, `429` with `Retry-After` and `rate_limited`), the address taken from the edge's header and believed only from the edge, held in memory for the window only; at most 2 active jobs per client (S6);
- a shared HTTP cache (RFC 9111) of public `GET` answers by the tools' own headers (the classes of Goniec S3), never an answer to a request with a credential, never a `POST`;
- CORS: none by default; a deployment MAY list origins for public `GET`s, never with credentials; a tool behind Latarnik keeps its own CORS empty;
- headers: client requests lose every `X-Forwarded-*`, `Forwarded`, `X-Real-IP` and `CF-Connecting-IP`, and every credential (`X-API-Key`, `X-Admin-Key`, `Authorization`, cookies) but the one the route uses (`X-Admin-Key` on `/api/admin/…`, `X-API-Key` on a route of S2's key rows, Archiwista's cookie and CSRF header on its host); Latarnik sets `X-Forwarded-For`, `X-Forwarded-Proto` and `X-Forwarded-Host`;
- logs as DEV-12.4 to DEV-12.9 with Nogat's `nogat_logging.py` and no address (DEV-12.5); each tool keeps its own;
- no accounts or roles in levels 1 and 2 (question 3).

L3. **Flows** (level 2). A flow is a named, fixed list of steps declared in Latarnik's repository, one file per flow: each step one catalog command of one service, each option a literal, an input of the flow, or a JSON Pointer (RFC 6901) into an earlier step's answer; no condition, loop, arithmetic or geometry. Latarnik checks each flow at start against the services' catalogs (commands, option names and types) and against the registry: each passage between two tools is an exchange the registry declares (HUB-2.6). `POST /api/v1/flows/<name>` with the inputs starts a Latarnik job; its result, `latarnik-flow/1`, holds the inputs and per step the service, its version, the command, the options and the tool's answer as given, with the tool's `attribution` and `terms_notice` (DEV §20), so each number names the step that made it. Values pass by reference where a tool has one (a store version for a series, a hand-off whole) and by value otherwise. A failed step ends the flow `failed` and keeps the answers before it.

L4. **One deployment, one release set.** Latarnik is a member of the release set released with it (REL-6.1; the author names the members, ECO-074), an app on its own lock, since it imports no tool; a deployment runs Latarnik and the services of one set. At each refresh of L1 it compares each service's `version` with the set's, and a service of another version is named in `/api/v1/server` and the log and not routed; flows are checked against the same versions.

L5. **The GUIs' files.** In a deployment one process per tool serves its API, its page routes and its GUI's files (as `<tool> gui serve` does on 127.0.0.1; the install contract's rule 1), the files' origin. Latarnik keeps in its cache what the tool's headers make fresh for a while (`max-age`, `immutable`: Obserwator's versioned files) and never a `no-cache` answer, so every page reaches the tool as the client sent it and the tool still counts its page views and visitors (DEV-15.11; Obserwator counts a page served with `200`), keeps its regulamin, feedback and admin. Rejected: reading the files from the tools' installed packages through `nogat.gui` (Latarnik would share the tools' environment, and Hydrograf in Docker has no package); exporting the files into Latarnik's directory at every update (a deployment step per tool and release).

L6. **Until level 1.** Once its step below is done, each tool is one process on its one host, which the tunnel already maps; a tool with two processes on one host, Obserwator after the Goniec plan's D1, gets the tunnel's path rules: `/api/v1/*`, `/ogcapi/*` and `/health` to `obserwator server`, the rest to `gui serve`. A rule forwards the full path, so `/api/v1` on a GUI's own host needs no Latarnik; `/<tool>/v1/` on a shared host (a prefix to strip, possible only with the edge's URL Rewrite Rules) and the list of all services wait for Latarnik. Level 1 replaces the rule of every host with one: every host to Latarnik.

L7. **Engine**, for Latarnik's first ADR: Python with Starlette, httpx and uvicorn, like the tools' servers, with Nogat's `nogat_logging.py` and the limit of DEV-15.9. Rejected: Caddy or nginx with a generated configuration (the rules of S2, the problem documents of a `429` and the logs of DEV-12.4 would need plugins or a second program; nginx in front keeps no log, DEV-12.8).

## Risks

| Risk | Effect | Mitigation |
|---|---|---|
| Latarnik in front of every public surface | Latarnik down, every service unreachable | each tool still runs alone; the tunnel's rules of D0 are the fallback; Latarnik's health in `/api/v1/server` |
| Public duties in Latarnik and in each tool | limits and logs drift | one reference module for logs (DEV-12.9), DEV-15.9 for limits; the tools keep theirs as the backstop |
| A shared cache before the tools | a stale or private answer served, a page view lost | public `GET`s by the tools' own headers only, never `no-cache` ones, never with a credential; the catalog's `effects` exclude the rest (S2, L5) |
| Forged forwarded headers on the host | a client's limit escaped or another's address used | tools on loopback only, Latarnik strips them; variant B before a tool leaves the host |
| Public computation on Hydrolog's server | its CPU exhausted | two workers and 30 s as today, 2 jobs per client, the limit |
| Obserwator's analyses over HTTP | a build that needs a running server | the program kept for a person alone, and for the build unless question 5 says otherwise; jobs end `interrupted` and the build resumes (ECO-073) |
