## Answers in short

- **The other services.** Each keeps running alone, unchanged for a person on one computer (Zen 10). Behind Latarnik a tool's server listens on 127.0.0.1, takes the client's address only from Latarnik's forwarded headers, writes relative links (absolute ones in OGC API, S5) and answers `nogat-server/1`; Latarnik adds the public duties once for all (caching, CORS, logs and the limit of its own host, L2) and never serves more than a tool does (S7, the table per tool).
- **Talking through the API.** One address: `GET /api/v1/server` lists the services and the base of each one's API; a command is called at `/<tool>/v1/<group>/<verb>` under the name its tool's catalog gives it, the tool's envelopes and errors passed through unchanged; long work is a job, `nogat-job/1`; a chain of several tools is one call, `POST /api/v1/flows/<name>` (level 2).
- **Computation apart from the GUIs.** Yes. Every GUI becomes files that call their tool's `/api/v1`, and every number comes from a tool's server: Hydrolog's for hydrology, Obserwator's for station data, Hydrograf's for terrain, Kartograf's for download plans. Today two GUIs compute inside their own GUI server behind a private API (Obserwator, Hydrolog), while Hydrograf's and Archiwista's are already files over their APIs (Facts).

## Design

### L0. Optional, and every tool alone

Latarnik is a new project (`https://github.com/Daldek/Latarnik`, which the author creates: on 2026-11-24 `git ls-remote` finds no such repository; profile `app`), optional in every deployment. Every tool keeps its CLI, MCP, library, server and GUI, `<tool> gui serve` one command on 127.0.0.1, and depends on nothing of Latarnik; Latarnik imports no tool and reaches each over HTTP only. Latarnik computes nothing: it routes, checks, limits, caches, logs and chains calls; a step that needs logic (a condition, arithmetic, geometry) is a tool's command.

### S. What a tool's server provides

S1. **Versioned REST from the catalog.** Every command with a route at `/api/v1/<group>/<verb>` (AGI-6.1); `server` and `jobs` are reserved and never a catalog group. The route is the catalog's: commands-1 and command-list-1 gain an optional `rest` (`{method, path, key}` or `null`, `key` as S2 says), and command-list-1 entries `effects` and `check` (additive, AGI-4.1; Obserwator's list carries them flat today). `rest.method` is `POST` for a read-only command whose inputs a URL cannot carry (an object such as a geometry or a network, a long array such as a series); such a route stays read-only and needs no key (an amendment of AGI-6.1). A route released as `GET` keeps its method (REL-1.1): an input a URL cannot carry comes with a new command (F1). OpenAPI also at `/api/v1/openapi.json`, Archiwista's place, with a relative `servers` URL, so that it reads right through a prefix (an amendment of AGI-6.2). An option with `path_role` is local: a server refuses it, as Obserwator's refuses server and local options (`api/routes/commands.py:29`), and takes its inline form.

S2. **The catalog decides access and caching** of each command as the server serves it, in the tool's server and again in Latarnik. A server refuses every option with `path_role` (S1), so a command whose only writes go to such options is read-only there and answers inline or as an attachment (DEV-19.21): Hydrolog's ten writing commands, which its catalog marks not `read_only` for any output path (`src/hydrolog/catalog/spec.py:586-588`, `:925-938`). Each entry of the server's command list says how it serves the command, `rest.key`: true when a run changes something on the server (its store, its files) or when the tool keeps a read-only command for its operator (a heavy one, such as Hydrolog's `commands batch`). Latarnik reads it from `/api/v1/commands/list` at each refresh (L1).

| Command as served | Access | Latarnik caches |
|---|---|---|
| read-only, no `network` | public | by the tool's `Cache-Control`, `ETag` and `Vary`, `public` answers only |
| read-only, `network` | public only through the tool's own cache of the provider: a snapshot or a cache per key of bounded age, as Obserwator's GUI has (`gui/_live.py`); never one provider request per client request | at most for the cache's remaining life |
| a plan, `POST …?check=true` of a command that is its own `check` | public where the tool serves plans: Kartograf's under its plan limits (its D5); Obserwator's public mode refuses them (Goniec S2) | no |
| a run whose `rest.key` is true | the tool's key, `X-API-Key` (the authentication of AGI-6.5), required by Latarnik on that route only (`401 unauthorized`) and checked by the tool in constant time; Latarnik keeps no tool's key; a tool MAY refuse such a run whatever the key (Kartograf's server, its D5) | no |
| `destructive` | the key and the command's own `force` | no |

S3. **Envelopes.** An answer is the tool's `<tool>-result/1` (AGI-4.2) or an attachment named as DEV-19.21 says; an error is `application/problem+json` with the fields of `<tool>-error/1` (AGI-6.3); texts follow `Accept-Language` (AGI-6.4); providers' lines as DEV §20. Latarnik passes bodies unchanged and answers its own errors in the same form: `rate_limited`, `unauthorized` (S2), `source_unavailable` for a service that is down or past its time, `not_found`, and `conflict` for its jobs and flows (S6, L4).

S4. **Discovery, `nogat-server/1`, at `GET /api/v1/server` on every server**, a tool's own and Latarnik alike, so that one request finds every service (agreed on 2026-11-24 with the review of the Goniec plan and with Kartograf's plan): `services`, one entry on a tool's own server and, on Latarnik, one per service it routes and one for itself (`tool` `latarnik`, `api` `{"1": "/api/v1"}` for its jobs and flows, its `terms`, `gui` `/`), each with `tool`, `version`, `api` (each major served and its base: `{"1": "/api/v1"}` alone, `{"1": "/obserwator/v1"}` behind Latarnik; a URL reference, absolute for a service on another host), `capabilities` (each tool's own words), `ogcapi`, `instance`, `terms`, `attribution`, `terms_notice` (the Goniec plan's S4) and `gui`, the address of its GUI that `[nogat.gui]` of `nogat.toml` gives (DEV-15.4, DEV-18.1), where it has one; on Latarnik each routed entry also has `state`: `ok`, `other_version` (routed, used by no flow, L4) or `unreachable` (the last refresh did not reach it, and its routes answer `source_unavailable`), and the document has `release_set` and `flows` (the names `GET /api/v1/flows` describes). The schema `schemas/exchange/server-1.schema.json`, additive within `/1` (AGI-4.1). A GUI finds its own API base as its tool's entry there, one request on either server (Kartograf's D7).

S5. **Behind Latarnik.** A server listens on 127.0.0.1, or on the compose network in a container (the install contract's rule 12; Obserwator's REST default changes); it takes the client's address and scheme only from `X-Forwarded-For` and `X-Forwarded-Proto` sent by a trusted proxy, set by one setting, `127.0.0.1` by default (uvicorn's `FORWARDED_ALLOW_IPS` in Obserwator and Hydrolog, `trusted_proxies` in Archiwista), the install contract's rule 3. Hydrograf, whose API sits behind its own nginx in Docker and believes only `X-Real-IP` and `CF-Connecting-IP`, from any loopback or private hop (`backend/api/traffic.py:20-26`, `docker/nginx.conf:193`), has nginx pass `$proxy_add_x_forwarded_for` and takes the right-most address that is no such hop, as Archiwista takes the right-most that is no trusted proxy (`security.py:861-889`). A server writes relative `Location` headers and links (a job's `Location: jobs/<id>`), so its documents read right behind any prefix and Latarnik rewrites no body, except the links of OGC API, which are absolute, built from `X-Forwarded-Proto` and `X-Forwarded-Host`, since QGIS uses an `href` as it comes (Facts); `/ogcapi/` is therefore served on the tool's own host, where Latarnik adds no prefix. Its own limits (DEV-15.9) and logs (DEV §12) stay as the backstop.

S6. **Jobs, `nogat-job/1`**, a new contract on Archiwista's model:

- `POST /api/v1/jobs` with `{"command": "<group> <verb>", "options": {…}}`, access as S2 gives for that command, which the tool decides from the body (Latarnik passes `X-API-Key` on this route and reads no body), answers `202`, `Location: jobs/<id>` and the job's document;
- `GET /api/v1/jobs/<id>` answers `nogat-job/1`: `id`, `tool`, `command`, `state` (Archiwista's seven), `progress` (`done`, `total`, optional), `created_at`, `started_at`, `finished_at`;
- `GET /api/v1/jobs/<id>/result` answers, once the job has ended, what the command's synchronous route would (the envelope, an attachment or the error's problem document), and before that `409 conflict` with the reason `job_running`;
- `POST /api/v1/jobs/<id>/cancel` answers `202`; `GET /api/v1/jobs/<id>/events`, server-sent events resumed after `Last-Event-ID`, MAY be served.

The id is 128 random bits and the only way to a job (no list of other clients' jobs). An ended job stays at least an hour, then `404 not_found` with the reason `job_expired`; a result of a person's choices is held in memory only (ECO-059); a restart ends a running job `interrupted`. Each client has at most 2 active jobs on each server, counted by that server; Latarnik counts only its own (L2). A command whose run can outlast a request carries `long: true` in its catalog (optional in commands-1) and is served as a job too. A route released with an answer within the request keeps it in `/api/v1` (REL-1.1: Obserwator's four below, released in v3); a route first released after this plan MAY serve the command only as a job, its synchronous form answering `409 conflict`, reason `run_as_job` (Hydrolog's new server, Hydrograf's `/api/v1`). MCP keeps its progress notifications (AGI-5.11). First jobs: Obserwator's `store sync`, `series build`, `analyses build`, `pmaxtp sync`; Hydrolog's `commands batch` and a large `route network`; Hydrograf's hydrographs and networks of large catchments; later Hydraulik's model runs.

On a GUI's host Latarnik passes every request to the tool's server, serving from its cache what may be cached (L5), so a GUI, its admin paths and the edge's Access rules are the same alone and behind Latarnik. L2. **At the door**, once for every service, what each public GUI does today on its own:

- limits per client address as DEV-15.9 on Latarnik's own host (300 requests in 60 s by default, `429` with `Retry-After` and `rate_limited`), the address taken from the edge's header and believed only from the edge, held in memory for the window only, and at most 2 active flows per client (its own jobs, S6); on a GUI's host the tool's own limit counts, since only the tool knows its static files and map tiles (Hydrograf's tiles at ten times its limit, Facts);
- a shared HTTP cache (RFC 9111) of public `GET` answers by the tools' own headers (the classes of Goniec S3), never an answer to a request with a credential, never a `POST`;
- CORS: none by default; a deployment MAY list origins for public `GET`s, never with credentials; a tool behind Latarnik keeps its own CORS empty;
- headers: client requests lose every `X-Forwarded-*`, `Forwarded`, `X-Real-IP` and `CF-Connecting-IP`, and every credential (`X-API-Key`, `X-Admin-Key`, `Authorization`, cookies) but the one the route uses (`X-Admin-Key` on a GUI host's admin paths, DEV-15.13; `X-API-Key` on a run whose `rest.key` is true and on `POST …/jobs`, S2, S6; Archiwista's cookie and CSRF header on its host); Latarnik sets `X-Forwarded-For`, `X-Forwarded-Proto` and `X-Forwarded-Host`;
- logs as DEV-12.4 to DEV-12.9 with Nogat's `nogat_logging.py` and no address (DEV-12.5); each tool keeps its own;
- no accounts or roles in levels 1 and 2 (question 3).

L3. **Flows** (level 2). A flow is a named, fixed list of steps declared in Latarnik's repository, one file per flow: each step one catalog command of one service, each option a literal, an input of the flow, or a JSON Pointer (RFC 6901) into an earlier step's answer; no condition, loop, arithmetic or geometry. Latarnik checks each flow at start against the services' catalogs (commands, option names and types) and against the registry: each step's service is a `depends_on` of Latarnik `via: [rest]` whose `exchange` names the documents the flow reads from it or passes to it (HUB-2.6; N1 lists F1's). `POST /api/v1/flows/<name>` with the inputs starts a Latarnik job; its result, `latarnik-flow/1`, holds the inputs and per step the service, its version, the command, the options and the tool's answer as given, with the tool's `attribution` and `terms_notice` (DEV §20), so each number names the step that made it. Values pass by reference where a tool has one (a store version for a series, a hand-off whole) and by value otherwise. A failed step ends the flow `failed` and keeps the answers before it.

L4. **One deployment, one release set.** A deployment runs Latarnik and the services of one release set. Latarnik, an app on its own lock since it imports no tool, is not installed by `nogat` (REL-6.1) and runs its suite on its own lock as Hydrograf does (ECO-077); it joins a set when the author names it among the members (ECO-074), proposed from the first set after it is `active` (N2). At each refresh of L1 it compares each service's `version` with the set's: a service of another version stays routed, since a pass-through changes none of its answers, and is named in `/api/v1/server` (`state` `other_version`, S4) and in the log, and a flow that uses it answers `409 conflict`, reason `other_version`, until the versions agree; members released outside a set, as Obserwator `v3.2.0` and Archiwista `v0.4.0` were on 2026-11-23 (REL-6.6), are this case.

L5. **The GUIs' files.** In a deployment one process per tool serves its API, its page routes and its GUI's files (as `<tool> gui serve` does on 127.0.0.1; the install contract's rule 1), the files' origin. Latarnik keeps in its cache what the tool's headers make fresh for a while (`max-age`, `immutable`: Obserwator's versioned files) and never a `no-cache` answer, so every page reaches the tool as the client sent it and the tool still counts its page views and visitors (DEV-15.11; Obserwator counts a page served with `200`), keeps its regulamin, feedback and admin. Latarnik drops its cache of a service when a refresh of L1 finds the service's `version`, `terms` or lines changed, so a release or new lines reach clients within a minute; a deployment that keeps the edge's cache of the Goniec plan's S6 purges it at each deployment, as that plan says. Rejected: reading the files from the tools' installed packages through `nogat.gui` (Latarnik would share the tools' environment, and Hydrograf in Docker has no package); exporting the files into Latarnik's directory at every update (a deployment step per tool and release).

L6. **Until level 1.** Once its step below is done, each tool is one process on its one host, which the tunnel already maps; a tool with two processes on one host, Obserwator after the Goniec plan's D1, gets the tunnel's path rules: `/api/v1/*`, `/ogcapi/*` and `/health` to `obserwator server`, the rest to `gui serve`. A rule forwards the full path, so `/api/v1` on a GUI's own host needs no Latarnik; `/<tool>/v1/` on a shared host (a prefix to strip, possible only with the edge's URL Rewrite Rules) and the list of all services wait for Latarnik. Level 1 replaces the rules of a host with one, the host to Latarnik, host by host as D1 says.

L7. **Engine**, for Latarnik's first ADR: Python with Starlette, httpx and uvicorn, like the tools' servers, with Nogat's `nogat_logging.py` and the limit of DEV-15.9. Rejected: Caddy or nginx with a generated configuration (the rules of S2, the problem documents of a `429` and the logs of DEV-12.4 would need plugins or a second program; nginx in front keeps no log, DEV-12.8).
